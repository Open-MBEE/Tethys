| F-D01 | 2026-10-22 | OpenSysML v0.10.1-2054 / pilot at the vendored pin | `model/probes/F-D01-positional-parameter-redefinition.sysml`: `action def Step { in input; out output; } … action stepA : Step { out :>> output; }` | OpenSysML `-validate -strict -warnings-as-errors` accepts the file. The pilot reports `Redefining feature must have a compatible direction` on `output`, and in the full model (an earlier draft of `TethysMeridian::SciencePipeline`) also failed to resolve `stepA.input`. | The parameters of a step redefine the parameters of its behavior *by position* (KerML 8.4.4.6 / SysML 7.17.2: the owned parameters of an action usage redefine, in order, those of its action definition). The first parameter written in `stepA` therefore redefines `input` as well as, explicitly, `output`; an `out` redefining an `in` is a direction conflict the validator must report. OpenSysML is missing the diagnostic. The model writes `in :>> input; out :>> output` so both validators agree. | open — missing diagnostic in OpenSysML (pilot correct) |
| F-D02 | 2026-10-22 | OpenSysML v0.10.1-2054 / pilot at the vendored pin | `model/probes/F-D02-constructor-overrides-bound-value.sysml`: `item def A { attribute x : Integer = 1; } … send new A(x = 2) to receiver` | OpenSysML accepts the file. The pilot reports `Cannot override a binding feature value` on `x = 2`. OpenSysML does report the same override when it is written as a redefinition (`attribute :>> x = 2`), with a hint to write `default =`. | A feature value written with `=` is a binding that every specialization inherits; a constructor argument that rebinds it is the same conflict as a redefinition that rebinds it (KerML 8.3.4.9 FeatureValue, SysML 7.5.3 default feature values). OpenSysML should report the constructor form as it reports the redefinition form. The model omits the fixed attributes from every `new …(…)` argument list (`TethysOperations::OperationsScenario`). | open — missing diagnostic in OpenSysML (pilot correct) |
| F-D03 | 2026-10-22 | OpenSysML v0.10.1-2054 / pilot at the vendored pin | `model/probes/F-D03-allocate-owned-action.sysml`: `part def Plan { occurrence pass1 : Pass; action owned : Downlink; allocate owned to pass1; }` | The pilot reports `Must be an accessible feature (use dot notation for nesting)` on `owned`; the same allocation written with `perform action performed : Downlink; allocate performed to pass1;` passes. OpenSysML accepts both. | Both ends are owned features of `Plan`, the allocation's owning type, so both are accessible connector ends (KerML 8.3.4.8 Connector, validateConnectorTypeFeaturing); whether the action usage is performed or owned does not change its featuring type. The pilot's diagnostic looks spurious. The model uses `perform action` for the pass-plan activities (`TethysOperations::DailyPassPlan`) so both validators accept it; the plain form is kept in the probe. | adjudicated — pilot right by the letter of the spec: KerML 8.3.4.5.3 `checkConnectorTypeFeaturing` ("Each relatedFeature of a Connector must have each featuringType of the Connector as a direct or indirect featuringType") read with SysML 8.3 `deriveUsageMayTimeVary` ("If isComposite = true, it does not specialize Actions::Action"): the `allocate` in a part def is time-varying and featured by the part's snapshots, a composite action usage is featured by the part itself, so an owned, non-performed action usage is not a valid allocation end; the model's `perform action` form in `TethysOperations::DailyPassPlan` is the correct one; probe kept, the pilot diagnostic is not spurious |
| F-D04 | 2026-10-22 | OpenSysML v0.10.1-2054 | `model/54-icds-tooling.sysml`: `IcdParameters` — `Project(source = WhereType(source = OwnedElements(source = Named(qualifiedName = icd)), type = "AttributeUsage"), properties = ("name", "type", "value"))` | `-render-document` fails with `query … references unknown property value`; the projectable properties are the KerML/SysML metaclass properties (`name`, `type`, `documentation`, `qualifiedName`, `direction`, …) and a `Column` cell reads a *feature of* the row element, not the row element's own feature value. An ICD parameter table therefore lists the parameters but cannot show the values the model binds to them. | A document query over attribute usages should be able to project the value bound by the usage's `FeatureValue` (KerML 8.3.4.9; SysML 7.5.3), e.g. as a `value` property or a `Column(path = …)` form, since that is what an ICD table publishes. | fixed in pin — OpenSysML #1385 (develop `5cd37f288`): `Project(… properties = ("name", "type", "valuation"))` gives the bound value with its unit (tug–inspector ICD 28 [V], 15 [W], 9600 [bit/s]; launch ICD 1.666 [m] adapter, 58.8 [m/s²] axial); `model/54-icds-tooling.sysml` projects it and `runs/wpd-*-icd-document.txt` pin the tables |
