| F-D01 | 2026-10-22 | OpenSysML v0.10.1-2054 / pilot at the vendored pin | `model/probes/F-D01-positional-parameter-redefinition.sysml`: `action def Step { in input; out output; } … action stepA : Step { out :>> output; }` | OpenSysML `-validate -strict -warnings-as-errors` accepts the file. The pilot reports `Redefining feature must have a compatible direction` on `output`, and in the full model (an earlier draft of `TethysMeridian::SciencePipeline`) also failed to resolve `stepA.input`. | The parameters of a step redefine the parameters of its behavior *by position* (KerML 8.4.4.6 / SysML 7.17.2: the owned parameters of an action usage redefine, in order, those of its action definition). The first parameter written in `stepA` therefore redefines `input` as well as, explicitly, `output`; an `out` redefining an `in` is a direction conflict the validator must report. OpenSysML is missing the diagnostic. The model writes `in :>> input; out :>> output` so both validators agree. | open — missing diagnostic in OpenSysML (pilot correct) |
| F-D02 | 2026-10-22 | OpenSysML v0.10.1-2054 / pilot at the vendored pin | `model/probes/F-D02-constructor-overrides-bound-value.sysml`: `item def A { attribute x : Integer = 1; } … send new A(x = 2) to receiver` | OpenSysML accepts the file. The pilot reports `Cannot override a binding feature value` on `x = 2`. OpenSysML does report the same override when it is written as a redefinition (`attribute :>> x = 2`), with a hint to write `default =`. | A feature value written with `=` is a binding that every specialization inherits; a constructor argument that rebinds it is the same conflict as a redefinition that rebinds it (KerML 8.3.4.9 FeatureValue, SysML 7.5.3 default feature values). OpenSysML should report the constructor form as it reports the redefinition form. The model omits the fixed attributes from every `new …(…)` argument list (`TethysOperations::OperationsScenario`). | open — missing diagnostic in OpenSysML (pilot correct) |
| F-D03 | 2026-10-22 | OpenSysML v0.10.1-2054 / pilot at the vendored pin | `model/probes/F-D03-allocate-owned-action.sysml`: `part def Plan { occurrence pass1 : Pass; action owned : Downlink; allocate owned to pass1; }` | The pilot reports `Must be an accessible feature (use dot notation for nesting)` on `owned`; the same allocation written with `perform action performed : Downlink; allocate performed to pass1;` passes. OpenSysML accepts both. | Both ends are owned features of `Plan`, the allocation's owning type, so both are accessible connector ends (KerML 8.3.4.8 Connector, validateConnectorTypeFeaturing); whether the action usage is performed or owned does not change its featuring type. The pilot's diagnostic looks spurious. The model uses `perform action` for the pass-plan activities (`TethysOperations::DailyPassPlan`) so both validators accept it; the plain form is kept in the probe. | open — spurious pilot diagnostic to confirm against the pilot's own test suite |
