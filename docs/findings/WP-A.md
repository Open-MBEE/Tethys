# Findings — WP-A (requirements tree and verification programme)

Tool boundaries met while building `model/20`–`23`. Same columns as `docs/findings.md`; probes
live under `model/probes/` and are excluded from `make check`.

| id | date | build | construct | observed | expected (spec) | status |
|---|---|---|---|---|---|---|
| F-A01 | 2026-10-22 | OpenSysML develop 0a5fa2d (v0.10.1-2054) / pilot validator at the vendored pin | implicit subject position in `concern def` / `viewpoint def` | A `concern def` whose first member is a `stakeholder` parameter and that declares no `subject`, and a `viewpoint def` that frames such a concern, are rejected by the pilot with `Subject must be first parameter`; OpenSysML accepts both (probe `model/probes/F-A01-implicit-subject-position.sysml`). Declaring `subject s : Thing;` first makes both tools accept. | The two tools disagree, so one of them is wrong about `validateRequirementDefinitionSubjectParameterPosition` (SysML v2 Requirements constraints) when the subject is only implied: either the implied subject counts as a parameter that must precede the stakeholders (pilot) or the rule only applies to a declared subject (OpenSysML). The model declares the subject explicitly everywhere, which is correct under both readings. | open — tool disagreement, to adjudicate against the spec text |
| F-A02 | 2026-10-22 | OpenSysML develop 0a5fa2d (v0.10.1-2054) | requirement group: `requirement grp { require r00; … require r11; }` | `sysml -validate` on a package of twelve bare requirements and one requirement that `require`s all of them does not finish (killed after 10 min at 100 % CPU). Time grows about 8x per added member: 9 members 1 s, 10 members 9 s, 11 members > 60 s (probe `model/probes/F-A02-requirement-group-blowup.sysml`). Subjects, constraints and metadata make no difference; the pilot validates the probe in 4 s. In the model it surfaced as `TethysRequirementsL2::flightSegmentRequirements` with 16 `require`s. | Validation of a RequirementUsage with n nested `require`d requirements should be linear in n: each `require` is one RequirementConstraintMembership (SysML v2 Requirements, `requiredConstraint`) and nothing in the semantics composes them combinatorially. Slow path, not a wrong result. | open — OpenSysML performance defect; the model splits every requirement group to six members or fewer until it is fixed |
| F-A03 | 2026-10-22 | OpenSysML develop 0a5fa2d (v0.10.1-2054) | reading a variant's attribute: `Case::big.m` where `big` is a `variant part` of `variation part def Case` | `-instantiate VariantRead::holder -validate=VariantRead::holder` reports `assert constraint viaVariant could not be evaluated … cannot chain through non-instance member (variant)` while the same chain through a nested non-variant part (`cases.big.m`) holds (probe `model/probes/F-A03-variant-member-read.sysml`). `-satisfy` on an L2 requirement whose constraint read `TargetCase::large.mass` failed the same way. The pilot validates the construct. | A variant usage is a Usage with a bound value like any other member; a feature chain through it should evaluate to that value (KerML Feature chaining, SysML v2 Variability: a variant is a usage owned by the variation). Wrong result class: undetermined where a value exists. | open — OpenSysML evaluation gap; the model keeps the sized bodies in `TethysStakeholders::targetCases` (plain parts) and the `TargetCase` variation subsets them, so requirements read `targetCases.large.mass` |
| F-A04 | 2026-10-22 | OpenSysML develop 0a5fa2d (v0.10.1-2054) / pilot validator at the vendored pin | `expose A::*` in a `view` where package `A` has a `private import Lib::*` | OpenSysML reports `warning[name-conflict]: Duplicate of imported member name 'Y': Lib::Y (import all A::*), Other::Y (import all Other::*)` — the exposed set contains `Lib::Y`, which `A` only imports privately — and `-strict -warnings-as-errors` makes it an error (probe `model/probes/F-A04-expose-private-import-leak.sysml`). The pilot accepts the file. In the model every `expose TethysRequirementsL2::*` tripped this through L2's private imports. | Adjudicated: spec-mandated. SysML v2.1 §8.3.26.2 Expose: "Visibility is always ignored for an Expose (`isImportAll = true`)", and KerML 1.1 §8.3.2.5 `Namespace::visibleMemberships(…, includeAll = true)` follows the exposed namespace's private imports — so `expose A::*` does import `Lib::Y`, and two import-all exposes that both bring in `Y` are indistinguishable memberships the validator must report (KerML 1.1 §8.3.2.5 `validateNamespaceDistinguishability`). OpenSysML's warning is the spec's verdict; the pilot accepts only because its validator does not check distinguishability of imported memberships. (This supersedes the earlier reading of KerML 7.2.5, which governs `import`, not `expose`.) | adjudicated: spec-mandated; pilot accepts only because its validator does not check distinguishability of imported memberships — the V&V matrix views expose their members one by one, which is the model remedy |
| F-A05 | 2026-10-22 | OpenSysML develop 0a5fa2d (v0.10.1-2054) | `objective { verify r1; … verify r13; }` in a `verification def` | The F-A02 blow-up applies to `verify` members as well as `require` members: `make validate` took about 50 s with one objective of nine `verify`s and one of eight, and did not finish in 200 s once one objective held thirteen; splitting every objective to seven or fewer members brought the whole model back to 3 s. No standalone probe beyond F-A02's: `verify` and `require` are both RequirementConstraintMemberships of the owning requirement. | As F-A02: linear in the number of memberships. | open — same defect as F-A02; the model keeps every objective at seven `verify`s or fewer |
| F-A06 | 2026-10-22 | OpenSysML develop 0a5fa2d (v0.10.1-2054) / pilot validator at the vendored pin | `@VerificationMethod { kind = VerificationMethodKind::test; }` inside a `verification def` body | `-analysis` of a usage of that def reports `verdict: error — statement not executable: calculation body: `then` statement in a body is not executable`; the same def without the metadata usage, with it on the verification usage, or annotated from outside with `metadata VerificationMethod about Def { kind = …; }` runs and passes (probe `model/probes/F-A06-verification-method-in-body.sysml`). Both validators accept every form. | A MetadataUsage is an annotating element, not a step of the case's body; the body's result expression (`PassIf(…)`) should run regardless of where the annotation sits (SysML v2 Metadata; Verification Cases `VerificationMethod` "can be used as metadata annotating a verification case"). Wrong result: an executable case reports error. | open — OpenSysML execution defect; the model declares each case's method with `metadata VerificationMethod about` after the def |
