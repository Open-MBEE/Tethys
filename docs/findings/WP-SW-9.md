# Findings against OpenSysML — WP-SW-9 (software document set)

Same columns as `docs/findings.md`; ids are renumbered at integration. Probes under `model/probes/`;
each probe is pinned by a `sw-doc-probe-*` run in `scripts/runs.sh`. Tool: OpenSysML built from
source at develop `5cd37f288`, the pin of `scripts/fetch-tools.sh`; pilot 2026-08 / 0.62.0 for the
second opinion. The document vocabulary (`Document`, `Section`, `Table`, `Ref`) is OpenSysML's
`DocumentQueries` library, so the SysML v2 specification governs only the KerML constructs the
documents are written with (feature values, redefinition, namespaces); where no clause applies the
row says so and the finding is classified as a design consequence.

| ID | Found | Version | Construct | Observed | Expected (spec §) | Status |
| --- | --- | --- | --- | --- | --- | --- |
| F-SW901 | 2026-10-23 | OpenSysML 5cd37f288 | A document block's query argument bound to an attribute of the document rather than to a literal: `attribute root : String; … calc q : WidgetRows { in :>> root = root; }` with `part def OneDoc :> BoundByAttribute { :>> root = "F_SW901"; }` (probe `model/probes/F-SW901-query-binding-from-attribute.sysml`, runs `sw-doc-probe-query-binding`, `sw-doc-probe-query-binding-literal`) | `-render-document F_SW901::OneDoc` fails with `query F_SW901::WidgetRows binding root has type element, expected ScalarValues::String`; the same table with `in :>> root = "F_SW901"` renders. The file validates clean under `-validate -strict -warnings-as-errors`. | KerML 7.4.11 (Feature Values): a feature value is any expression, and `root` here is a feature reference to a String attribute whose value the specialising document binds. The document planner evaluates the binding statically and accepts literals only; nothing in the specification forbids the reference. Classification: **OpenSysML limitation** (design-time evaluation of bindings), not a spec disagreement. | Open. Consequence: a document family cannot share one section set parameterised by an attribute; the 24 design descriptions each bind their qualified names literally, which is why `model/94-software-documents-tooling.sysml` carries one definition per application and component. |
| F-SW902 | 2026-10-23 | OpenSysML 5cd37f288 / pilot 2026-08 | Two `verify` members of one objective referencing requirements of the same name, a system row and the software row derived from it: `verify sequenceClearance … verify F_SW902_Software::sequenceClearance` (probe `model/probes/F-SW902-same-named-verify-members.sysml`, run `sw-doc-probe-same-named-verify`) | OpenSysML strict: `error[name-conflict]: Duplicate of other owned member name` on the second member. Pilot: `warning: Duplicate of other owned member name`, no error. Writing the second reference by short name (`verify F_SW902_Software::'TM-003'`) is accepted silently by OpenSysML although the member's effective name is still `sequenceClearance`; the pilot warns on that form too. | KerML 8.3.2.5 (Namespace, `validateNamespaceDistinguishability`) with 8.3.2.4.3 (`Membership::isDistinguishableFrom`): two owned memberships of one namespace must be distinguishable, and a `verify` member with no declared name takes the referenced requirement's name as its effective name. The pilot and OpenSysML agree on the conflict (warning vs error is a severity choice); OpenSysML's silence on the short-name form is the only lenient spot. Classification: **spec-correct** for the rejection; **OpenSysML defect (lenient)** for the short-name form. | Open for the short-name leniency. Consequence: `GroundCommandTwoStepTest`, which verifies the system row `sequenceClearance`, does not also carry `verify` of the software row TM-003 of the same name; TM-003 stays verified by `CommandRoutingTest`, `ThrustArcControlTest`, `PowerManagementTest` and two system cases, and the omission is listed in `docs/coverage/WP-SW-9.md`. |
| F-SW903 | 2026-10-23 | OpenSysML 5cd37f288 | A document definition specialising another document (`part def Volume :> Base`) and adding blocks (probe `model/probes/F-SW903-inherited-blocks-render-last.sysml`, run `sw-doc-probe-inherited-order`) | The inherited blocks render, but after the specialising document's own blocks: `Volume` renders "Added block." before "Base block.". The base title must be written `:>> title default = …` or the specialisation cannot retitle (`feature-value-overriding`). | No specification clause: block order is the planner's (local members first, then inherited, `effectiveMembers` in `internal/ir/docplan`). KerML 7.3.4.x (Redefinition) would let a volume reorder only by redefining every base block. Classification: **design consequence**. | Not a defect — modelling note. Consequence: the requirements specification, the dictionary volume and the test plan specialise their base documents and their added cross-reference sections render before the inherited rows; the scope paragraph of each says so. `64-flight-dictionary-tooling`, `67-software-requirements-tooling` and `88-software-assurance-tooling` now declare their titles with `default =`. |
