# Argent software tables — the generator toolchain

The stage-2 software of the Tethys mission (the fictional Argent Flight Executive on the Kestrel
executive, the AABP-1 software bus, and the Meridian Operations Suite on the ground) is built on
tables generated from the SysML v2 model, not typed in by hand. This directory holds the generator,
the tables it writes and their tests. Nothing here is flight or ground software itself.

## Toolchain

| Piece | Where | Role |
| --- | --- | --- |
| Pinned OpenSysML `sysml` | `build/opensysml/sysml` (built by `make tools`, commit `5cd37f288fef171d62737d6045f4caff772b6014`) | Reads the model; `-convert api-json` writes it in the SysML v2 API's JSON element form |
| OpenSysML Python client | `build/software/venv` (installed by `make software-venv` from `build/opensysml-src/client/python`, the same checkout as the binary) | Pins the client to the tool; the tests run in this venv |
| Generator | `software/gen/` (Python ≥ 3.11, standard library only at run time) | `generate.py` drives `apijson.py` (streaming reader), `libids.py` (library ids), `extract.py` (normalisation), `emit_c.py`, `emit_py.py` |
| Generated tables | `software/generated/c/*.h`, `software/generated/python/argent_tables/*.py`, `software/generated/MANIFEST.sha256` | Committed; regenerated by `make software-generate` |
| Self-test | `software/generated/c/selftest.c` (hand-written) | Compiles every header with `-std=c11 -Wall -Wextra -Werror -pedantic` and checks the table invariants |
| Tests | `software/tests/` | pytest cross-checks against the pinned `runs/` figures |

```sh
make tools              # once: the pinned OpenSysML and pilot validators
make software-venv      # once: the pinned Python client + pytest into build/software/venv
make software-generate  # regenerate software/generated/ from model/ (≈ 40 s: 34 s conversion, 7 s extraction)
make software-selftest  # compile and run the C self-test
make software-test      # run the Python tests
make software-check     # the gate: regenerate into build/software/regen, fail on any drift, self-test, tests
```

`make check` is unchanged and model-only. `software-check` is a separate CI job in
`.github/workflows/check.yml` with the same tool-fetch steps.

## How generation works

1. `sysml -convert api-json -o build/gen/model.api.json model/*.kerml model/*.sysml` writes the
   whole model (64 files, ≈ 485 MB) in the API element form.
2. `apijson.read` streams that file one top-level element at a time and keeps a reduced record of
   every element whose id starts with one of the packages the generator reads
   (`TethysTugStructure`, `TethysOperations`, `TethysModes`, `TethysFdir`, `TethysFlightSoftware`,
   `TethysFlightDictionary`, `TethysFlightBehaviour`, `TethysFlightTiming`, `TethysSoftwareIcds`):
   265 132 of the model's elements, ≈ 285 MB resident, 7 s. The JSON is never loaded whole.
3. `extract.extract` turns the element graph into plain table data: a feature's value is the
   expression element it owns, read as a literal, an enumeration reference, a quantity (`value [unit]`),
   a sequence, or a reference followed to the feature it names (so `allowedModes = (coast, thrustingModes)`
   becomes the literal mode names). Standard-library types appear in the element form as name-based
   UUIDs; `libids.py` derives the same UUIDs from the library sources the tool bundles and names them.
4. `emit_c` and `emit_py` write the tables; `MANIFEST.sha256` lists every generated file with its digest.

Every file starts with a header comment naming the generator version, the model tool pin and the
model elements it was read from, and carries nothing else but data.

## The determinism rule

The same model and the same tool pin give byte-identical files. The generator sorts every table on
its identifier (opcode, point id, event id, packet id, parameter id, APID, register address) except
where declaration order is the meaning — transitions within a state machine, fields within a packet,
streams in the bus frame — and it writes no timestamp, no absolute path and no machine-dependent
value. `make software-check` is the proof: it regenerates into a scratch directory and diffs.
Floating-point values are written as Python `repr` of the model's literal, so `0.1 [Hz]` is `0.1`.

## Encoding choices (proposals, not decisions)

These constrain the flight software that will consume the C tables; each was chosen for the
reason given and can be changed in the emitter alone.

- Mode sets are 16-bit masks (`argent_mode_mask_t`, bit *i* = `TugMode` literal *i*); application
  sets likewise over `ApplicationName`. Fits the 16 modes and 12 applications in one word.
- Variable-length children (command arguments, packet fields, telemetry→packet membership, register
  maps, topic ends) are flat arrays with `first`/`count` indices in the parent row, so every table is
  `static const` with no pointers to allocate.
- Guards and effects are *named expressions*: a table of `(id, text)` per machine, where the text is
  the model's expression (`b.fraction < limits.batteryLowFraction`) and the id (`POWER_MANAGER_G2`)
  is what the flight software implements as a predicate or action. Transitions reference them by index.
- The `done` target of a completion transition is `ARGENT_STATE_DONE` (-2); no parent is
  `ARGENT_STATE_NONE` (-1).
- A telemetry point's sample rate per mode is not a 961 × 16 matrix: housekeeping points are sampled
  at the mode's `housekeepingPeriod` from the MLS-2 rate set, every other kind at its nominal `rate`
  (`argent_tables.telemetry.sample_rate_hz` is the reference implementation).
- Reals are `double`, counts `uint16_t`, flags `uint8_t`; strings are `const char *` literals.

## How stage-2 packages consume the tables

- Flight (C11): include the headers from `software/generated/c/`; they have no dependencies beyond
  `<stdint.h>`. The command service dispatches on `argent_commands[]` by opcode (sorted, so binary
  search works), the telemetry output builds packets from `argent_packets[]`/`argent_packet_fields[]`,
  the FDIR application reads `argent_limit_table[]`, the executive schedules `argent_scheduled_tasks[]`
  by partition and rate group, and each application's state machine runner walks its
  `argent_*_transitions[]` and implements the guard/effect ids.
- Ground (Python): `import argent_tables` from `software/generated/python`; the dictionaries are
  `NamedTuple` rows with `*_BY_*` lookup dictionaries, and `enums` are `IntEnum`s shared with the C
  values. A Go emitter is a third `emit_*` module when a package needs one.
- Ground (Python and Go, `software/ground/`): the Meridian Operations Suite imports `argent_tables`
  for everything table-driven (command building, flight-rule and sequence checks, decommutation,
  limits, pass planning, archive cataloguing) and the `ground` table for the model's flight rules,
  on-board sequences, component catalogue, stations and retention rules; its Go services import
  `software/generated/go/argenttables` (`emit_go.py`, same rows as the Python tables with exported
  fields and `*ByX` lookups). Model calculations are evaluated through the pinned client against a
  `sysml-grpc` built from the same checkout, never re-implemented. Gate: `make software-ground-check`.
- Regeneration after a model change: `make software-generate`, review the diff of
  `software/generated/`, commit the generator change and the tables together; CI fails on drift.
